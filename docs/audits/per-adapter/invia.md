# Audit: invia (critical)

## Shrnutí

The adapter (/Users/daniel/Library/CloudStorage/OneDrive-Osobní/Effistream/dovolenky/src/sources/invia.ts) POSTs exactly two hardcoded queries to https://www.invia.cz/search-results/ajax-boxes: (1) nl_country_id=[28] (Řecko — the only entry in VERIFIED_COUNTRY_IDS), nl_length_from/to 7–14, sort=c_price; (2) a country-agnostic "last-minute" query, d_start_from=today..+14d, sort=c_price. Both take page 1 only. Because sort=c_price is ascending and the adapter never paginates, the adapter deterministically harvests the ~31 CHEAPEST rows on the entire Invia catalogue and nothing else. Live run: 31 offers, min 151 / median 3 969 / max 11 890 Kč per person; only 4 of 31 are flight packages, 22 of 31 are self-drive, 27 of 31 have no departure airport, 31 of 31 have stars=null. Invia's own site reports 4 667 CZ-departure flight packages for Řecko alone, 2 785 for Turecko, 2 132 for SAE, 1 515 for Španělsko, 881 for Egypt, 645 for Maledivy (from 22 490 Kč/os). The adapter returns zero offers from every one of those except Greece, and its price ceiling (11 890) sits below where Invia's exotic catalogue starts. Field mapping is largely faithful — pricePerPerson is verifiably correct per person and all-in for the stated term (0/31 mismatches) and the DB's 151 Kč outlier is Invia's own published price, not a parse bug — but nights is systematically overstated on flight/bus packages, and stars + priceTotal are hardcoded null despite both being present in the card markup. The biggest CZ agency is effectively missing from the board.

## Nálezy k opravě

### 1.

COVERAGE / CRITICAL — page-1-only + cheapest-first sort caps the adapter at the bottom of Invia's catalogue. buildQueries() sends sort:'c_price' (ascending) on both queries and never paginates. Every ajax-boxes response I captured returns customData.searchProps = {isNextPageAvailable: true, itemsPerPage: 15, boxesFound: 15|16} plus an `offsets` cursor string. I re-POSTed the Greece body with the returned offsets ('hotel:0;traso:0;merlinX:0;traveltainment:0;invia:16;tui:0;itemsPerPage:15;boxesFound:16') and got 15 brand-new offers (5 769–11 890 Kč, e.g. Medusa/Kriopigi, Ambrosia Suites, Orfeas Blue Resort) with only the sponsored Giakalis card repeated — so pagination works and is simply not implemented. Result: the observed max price/person of 11 890 CZK is a structural artifact of the sort order, not the market.

### 2.

COVERAGE / CRITICAL — VERIFIED_COUNTRY_IDS contains exactly one country (28 = Řecko), so ~everything Invia actually sells is unreachable. Invia's own data-found_boxes_count for 2-adult CZ-departure flight packages: Řecko 4 667, Turecko 2 785, Spojené arabské emiráty 2 132, Španělsko 1 515, Egypt 881, Maledivy 645 — ~12 600 packages in six countries. The adapter returned 16 Greek offers and 0 from any of the other five. This is self-imposed, not a technical limit: I POSTed the identical body with nl_country_id:[31] (Turecko, id read off https://www.invia.cz/dovolena/turecko/) and the endpoint returned 16 real flight packages at 7 443–12 390 Kč/os (Club Nena, Leda Beach, Sun City Side…). The comment in the file says ids are not guessed because they are unverified — but the ids are published in data-search_params on each /dovolena/<country>/ landing page (recko=28, turecko=31, egypt=11, spanelsko=[30,9], sae=13, maledivy=79).

### 3.

COVERAGE / HIGH — the whole exotic/high-price band is absent, and the last-minute query degenerates into 1-night city hotel rooms. Maledivy starts at 22 490 Kč/os (645 offers) and SAE has 2 132 offers, versus an adapter ceiling of 11 890. Meanwhile the country-agnostic last-minute query, also cheapest-first, returned 15 rows priced 151–1 005 Kč: eleven of them are single-night accommodation-only stays (Citi Hotels Wrocław, Roomz Vienna Prater, B&B Budapest City, ibis Muenchen City West, Mamaison Bratislava, B&B Hotel Passau…). s_holiday_target:'tours' does NOT restrict the result set to packages — Invia labels these 'Pouze ubytování'. So the second of only two queries contributes essentially no holiday-package value.

### 4.

FIELDS / HIGH — `nights` is systematically overstated on flight and bus packages. parseCard uses daysBetween(checkInDate, checkOutDate) with a daysCount-1 fallback; when checkOutDate is present those two rules produce the same number, and it disagrees with Invia's own '<X> dní / <Y> nocí' label on 17 of the 40 cards that display one (always an overstatement: +1 for flights, +2 for buses, because Invia subtracts nights spent travelling). Concrete: https://www.invia.cz/hotel/recko/kos/giakalis-aqua-park-resort/ — JWT checkIn 20261011 / checkOut 20261019 → adapter nights=8; the search card reads '9 dní / 7 nocí' and the URL carries nl_nights=7 (outbound flight departs 11.10 at 19:25, so the first hotel night is 12.10). Bus example: Apartmány Voula, https://www.invia.cz/hotel/recko/chalkidiki/apartmany-voula/ — adapter nights=9, card reads '10 dní / 7 nocí'. This inflates the offer and skews any price-per-night derivation downward. The correct value is on the card as plain text.

### 5.

FIELDS / MEDIUM — `stars` is hardcoded null although the value is right there in the card. parseCard returns `stars: null` unconditionally. Every one of the 63 cards I parsed carries a stars value in the card markup ("stars":3.5 for Giakalis) and again in the GA4 payload as item_parameter_4 ('s:_3.5_r:_4.1_o:_0_p:_0'); 49 of 63 have a non-zero value (Invia uses half-stars, 0 = unknown). The hotel detail pages confirm it independently via GA4 view_item item_stars (Giakalis 3.0/3.5, 4-You Apartmanhotel 3.0, Camping L'Ultima Spiaggia 4.0). The DB's 'stars 100% NULL' is purely this omission.

### 6.

FIELDS / MEDIUM — `priceTotal` is hardcoded null although the group price is published on every card. parseCard returns `priceTotal: null`, but 59 of 63 cards carry data-page--search--serp-offer-id-storage-price-group-value (Giakalis: 23780 = 2 × 11890), the same value is in the offer URL as c_price_group, in the JWT as originalTotalPrice, in the GA4 item as price/value, and rendered on the card as '23 780 za všechny'.

### 7.

FIELDS / LOW — `departureAirport` can be a pipe-joined multi-airport string rather than an airport. The adapter takes GA4 item_parameter_3 verbatim; 4 of 63 cards return values like 'BUD|KRK|BTS|VIE', 'BUD|PRG|KRK|VIE', 'PRG|VIE', 'PRG|BTS'. Example: https://www.invia.cz/hotel/recko/chalkidiki/4-you-apartmanhotel/ — adapter departureAirport='BUD|KRK|BTS|VIE'; the card renders 'Budapešť, Krakov, Bratislava, Vídeň', i.e. Prague is not an option at all. Note the DB's '88% NULL airport' is NOT a parse failure — it is the coverage skew: 30 of 63 cards are own-transport offers that legitimately have no airport, and the adapter's cheapest-first bias loads up on exactly those.

### 8.

FIELDS / LOW — TRANSPORT_ID_TO_TRANSPORT misses transportationId 5. Seen once in live data (Hotel Siros, Greece page 2) → mapped to 'unknown'. mealId coverage was fine: all 63 cards used 4/5/6, which the map handles.

### 9.

DATA QUALITY / NOTE (not an adapter bug) — the DB's 151 Kč minimum is Invia's own published price. https://www.invia.cz/hotel/italie/sardinie-sardegna/camping-l-ultima-spiaggia/ literally displays 'od 151 Kč za os.' for pá 11.9. – so 19.09.2026 (9 dní), Bez stravy, Pouze ubytování, tour operator 'Za sluncem s.r.o.'; the JWT carries originalTotalPrice 302.0 and the URL c_price_unit=151&c_price_group=302. The adapter reproduces it faithfully. It is still a landmine for a deals board, because cheapest-first sorting guarantees this class of broken tour-operator price will always be at the top of what Invia contributes.
