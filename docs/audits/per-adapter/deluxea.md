# Audit: deluxea (high)

## Shrnutí

The adapter GETs 12 hardcoded exotic listing pages (https://www.deluxea.cz/hotely-<slug>/), parses each `.single-item` card's `form.hotel-comparator-form[data-json]`, takes the nights-keyed `total` as pricePerPerson and reads name/stars/country/locality/URL from the static card HTML. The mechanics are sound and the price mapping is genuinely correct — I verified `total` really is the all-in per-person figure the site shows ("Kč / osoba"), and it matches the offer's own detail page to the koruna. The price band is right too (28k–190k CZK, median 68k), so this is not a "returns cheap domestic stays" failure. Two real problems, though. (1) Coverage: the site's sitemap lists 55 destination listing pages and 1011 hotel detail pages; the adapter queries 12 slugs, page 1 only, and 7 of those 12 return zero, so the live run yields 32 offers from 5 countries — about 3% of the catalogue. Whole segments never get requested (Řecko 74 hotels, Katar 22, Keňa 26, JAR 23, Itálie 26, Sardinie 22, Chorvatsko 22, Jordánsko 19, Fidži 17, Polynésie 16, Omán 16 …), and I confirmed those pages do carry priced offers. (2) departureDate is not a real departure: every one of the 32 offers carries 2026-09-10 because that is the hardcoded default of the site's price-calculator form, unchanged between the repo's 2026-07-07 fixture and today. That makes the "Odlet" column and date sorting meaningless for this source, and because src/web/api.ts and src/core/digest.ts drop offers via hasDeparted(), all 32 Deluxea offers will silently vanish from the board on 2026-09-11 unless the site's static default moves.

## Nálezy k opravě

### 1.

departureDate is a site default, not a real departure date — all 32/32 live offers report 2026-09-10. The value comes from the calculator form's hardcoded default input `<input type="text" name="date" … value="10.09.2026">` (the same string feeds data-json's `date_from`), and the datepicker is configured `minDate: dateToday`, i.e. the user picks any date they like. Proof it is static and not a rolling window: the repo's own fixture tests/fixtures/deluxea/hotely-maledivy.html, saved 2026-07-07, has value="10.09.2026" on all 8 cards, and the live page fetched today 2026-07-29 has the identical value="10.09.2026" — 22 days apart, zero movement. Verified on https://www.deluxea.cz/mauricius/hotel-heritage-le-telfair/ and https://www.deluxea.cz/hotely-maledivy/. Consequence in this codebase: src/web/api.ts:201, src/web/api.ts:393 and src/core/digest.ts:37 all filter with hasDeparted(r.departureDate, now), so on 2026-09-11 every Deluxea offer drops off the board and out of the digest at once; src/core/market.ts:392 also uses departureDate windows for the reference ladder, which a constant fake date skews.

### 2.

Only page 1 of each listing is read, and the listings are deeply paginated. The maledivy page carries a Nette paginator with pages 1–12 (`/hotely/?num=N&view=grid&destination=4&do=changeSide`), matching the 95 maledivy hotels in the sitemap; the adapter takes 8. I fetched page 2 with a session cookie (HTTP 200, 8 cards) and it contained 7 fully-priced offers the adapter never sees: totals 49 470, 54 320, 67 720, 70 070, 81 500, 91 620 and 165 700 CZK. Řecko's paginator goes to page 10, Itálie to 4, Katar to 3.

### 3.

43 of the site's 55 destinations are never requested. The sitemap (https://www.deluxea.cz/sitemap.xml, 200, 183 KB) lists 55 `/hotely-<slug>/` pages; LISTING_SLUGS in src/sources/deluxea.ts:73-86 has 12. Missing slugs include recko (74 hotels), katar (22), kena (26), jihoafricka-republika (23), italie (26), sardinie (22), chorvatsko (22), turecko (22), jordansko (19), spanelsko (18), reunion (17), fidzi (17), polynesie (16), oman (16), portugalsko (14), kypr (13), finsko (12), cerna-hora (12). These are not empty pages: https://www.deluxea.cz/hotely-recko/ page 1 alone yields 8 fully-priced cards (totals 42 130, 50 440, 53 170, 54 870, 56 620, 69 430 …) and https://www.deluxea.cz/hotely-italie/ yields 2 (42 170, 67 950). Three extra fetches (recko p1, italie p1, maledivy p2) surfaced 17 verified priced offers against the adapter's whole current output of 32.

### 4.

7 of the 12 slugs the adapter does fetch return zero offers, so 245 sitemap hotels produce nothing: emiraty (80 hotels), bali (36), sri-lanka (36), vietnam (31), tanzanie (30), dominikanska-republika (17), mexiko (15). Two distinct causes, both confirmed by parsing the live HTML: on bali, sri-lanka and dominikanska-republika 0 of 8 cards carry a data-json attribute at all (the comparator form is rendered without it), while on emiraty, vietnam, mexiko and tanzanie the data-json exists but prices are `{"7":"-"}` with total `Cena na vyžádání`. The second group is a defensible skip (there genuinely is no price on the page); the first group is a parse assumption that simply does not hold for those destinations. Same effect on a queried, productive slug: /hotely-thajsko/ has 8 hotel anchors but only 2 carry data-json, so 6 Thai 5* resorts are dropped and Thajsko contributes 2 offers.

### 5.

Minor: nights is the site's "Nocí v hotelu" value (the data-json key), while the trip itself is longer. For Heritage Le Telfair the same data-json says date_from 10.09.2026, date_to 19.09.2026, days 10 — the board will render "10.09.2026, 7 nocí" for a trip that returns on the 19th. Defensible because it mirrors the site's own label, but any price-per-night comparison against sources that count nights-away will flatter Deluxea.

### 6.

Minor/informational: claimedOriginalPrice and claimedDiscountPct are null on 32/32 offers because `old_total` is literally 0 on every card observed across 12 destinations (and on both saved fixtures). This matches the adapter's own docstring, so it is not a mapping bug, but it does mean Deluxea can never contribute a claimed-discount signal — the discount branch at src/sources/deluxea.ts:179-188 is only ever exercised by a synthetic test card.

## Adversariální ověření

- **POTVRZENO** (medium): CONFIRMED, and the mechanism is stronger than reported. I fetched /hotely-maledivy/, /hotely-mauricius/ and /hotely-thajsko/ live today with a Chrome UA (all HTTP 200) and inspected the markup myself. The data-json the adapter parses does not hang off an offer record — it hangs off a price-calculator widget: the block is introduced by the comment "Quick calculation in the area", the element is form.hotel-comparator-form inside div.comparator-simple, and EVERY input in that form is at its default value: input name="date" value="10.09.2026", select name="nights_from" with <option value="7" selected>, first room option selected, food "Snídaně" selected, transfer_include "Superior auto" selected, delegate_include and filter_airlines_select defaulted. The rendered data-json echoes those same defaults back: "meal":{"7":"Snídaně"}, "transfer_name":{"7":"Superior auto"}, "date_from":{"7":"10.09.2026"}. So date_from IS the form's default date input, and the "7" nights key that the adapter uses for `nights` is the nights_from select's default — neither is per-offer term data.

Invariance independently reproduced: live today every card on all three pages carries date_from={"7":"10.09.2026"} / date_to={"7":"19.09.2026"} (8 Maldives, 6 Mauritius, 2 Thailand); the repo's committed fixtures from 2026-07-07 (hotely-maledivy.html, hotely-zanzibar.html) carry the identical pair 8x each. 22 days, zero movement, and identical across Zanzibar and the Maldives, which have opposite seasons — that kills the "next available term / season start" explanation. The datepicker init is `minDate: dateToday` with `dateToday = new Date()`, i.e. the user picks any date from today onward. I also ran parseDeluxeaListing offline over the three live HTML files: 16/16 offers came out departureDate=2026-09-10, nights=7, with prices varying normally (28 440 – 190 040 CZK), matching the auditor's 32/32.

None of the standard false positives apply. (c) intentional/documented: the header comment at lines 44-46 documents "date_from/date_to {"7":"10.09.2026"} DD.MM.YYYY → parseCzDate → ISO departureDate" and "nights come from the price-dict KEY" as if they were genuine per-offer term data; it never states they are global form defaults, so this is a mistaken belief, not documented design. (a) genuinely-unpublished field: Deluxea's listing really does not publish a per-offer departure term, but the honest mapping for that is null, not a constant echo of a form default that downstream code then treats as a real term. (b) teaser-vs-cheapest and (d) dedupe are irrelevant — the price mapping (total = hotel price + tickets) is correct, only the date/nights are defaults.

One consequence in the report is overstated and I corrected it. src/core/ingest.ts:21 (normalizeDeparture, commit 4bcfbdf) nulls a past departure date at ingest on both write paths, so Deluxea offers will NOT all drop off the board and digest permanently on 2026-09-11 — they will persist as "volný termín"; the vanish window is at most one scan interval. The lasting harm is different but real: from that point every Deluxea row carries departureDate=null, and matchesDepartureMonth / matchesDepartureWithinDays (src/core/filters.ts:24-35) both return false on a null date, so the entire source stops matching any profile that sets departureMonths or departureWithinDays. And the harm already exists today: all 32 rows share one identical constant termín, so a profile with departureWithinDays <= 42 or departureMonths not containing 9 excludes 100% of Deluxea, the board's "Odlet" sort and TERMÍN column show one date for the whole source, and market.ts's month buckets (line 120/203) and ±30-day hotel window (167-168) only ever see Deluxea in 2026-09.

Severity medium rather than high: the value is not a fabricated price (the quoted figure genuinely is the 10.09.-19.09.2026 package), nothing crashes, the ingest date hygiene cushions the cliff, and this is one of 16 sources — but the field is systematically wrong for 100% of the source's rows and is load-bearing for profile matching, sorting and the reference ladder.

2. The design spec agrees. docs/superpowers/specs/2026-07-04-dovolenky-design.md §16.1 row 13: "GET country listingy (/hotely-<slug>/, slugs ověřit živě ze sitemap; ~8-12 exotických stránek/scan)", and the politeness footer of §16.1 budgets "Deluxea ~10-12" requests, with a project target of ~50-250 requests/run.
