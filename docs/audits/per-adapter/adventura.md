# Audit: adventura (high)

## Shrnutí

The adapter GETs https://www.adventura.cz/sitemap.xml, keeps only clean /zajezdy/{id}-{slug}/ detail pages whose slug matches one of 31 hardcoded EXOTIC_SLUG_TOKENS, sorts them lexicographically, takes the first MAX_DETAILS=25, and parses table.date-list on each (one <tr class="heading"> = one departure term = one offer). Field parsing is genuinely healthy: I diffed 9 parsed offers across 4 live pages against the pages themselves and every price, original price, discount %, departure date and nights matched exactly, transport/board are read from the correct "V ceně zahrnuto" block, and a sold-out term ("Uzavřeno", no price) is correctly skipped rather than emitted at 0 Kč. The problem is coverage, and it is structural rather than intermittent. filterExoticTourUrls found 64 exotic tours in the sitemap; the adapter fetches the lexicographically first 25. Because every exotic tour id is 5 digits, lexicographic order equals ascending numeric id, so the identical 25 lowest-id tours (11579…12114) are fetched on every single run and the 39 tours with id >= 12117 are fetched never — the log line "39 skipped this run" implies a rotation that does not exist. On top of that, the substring token list misses Czech declined slug forms, hiding another 6 in-scope tours before the cap even applies. Net effect: roughly 45 of ~70 in-scope Adventura tours are permanently invisible, and 10+ countries from the project's own "exotika" watch profile (Kuba, Zanzibar, Keňa, Madagaskar, Mauricius, Kapverdy, Maledivy, Indonésie, JAR, Filipíny) produce zero offers even though Adventura has live, bookable tours in all of them. Adventura is not missing from the board — it contributes 34 correctly-priced 63k–144k CZK exotic tours — but well over half of what it sells can never reach the board.

## Nálezy k opravě

### 1.

PERMANENT (not per-run) 25-of-64 blind spot. fetchOffers does `exoticUrls.slice(0, MAX_DETAILS)` on the output of `filterExoticTourUrls`, which returns `[...seen].sort()` — a stable lexicographic sort. All 64 exotic tour URLs carry 5-digit ids, so lexicographic order == ascending numeric id, and the slice always yields the same 25 lowest-id tours (11579-dominikanska-republika-na-kole … 12114-japonsko-nejen-pro-gurmany). The 39 tours with id >= 12117 are never fetched on any run, so they can never enter the DB. Live run 2026-07-29 returned 34 offers from 23 pages; the 39 skipped URLs are listed in the sitemap and are live. Raising the cap is cheap: 64 pages at the 3 s host gap is ~3.5 min against a 2 h scan cadence.

### 2.

10 countries from config/watch.yaml's `exotika` profile get ZERO offers despite Adventura selling live tours in each, purely because those tours sit past the cap: Kuba (/zajezdy/12668-kuba-na-katamaranu/, /zajezdy/12931-kuba-autenticka/), Zanzibar (12356-safari-a-migrace-v-np-tanzanie-a-zanzibar, 12358-narodni-parky-tanzanie-a-ostrov-zanzibar), Keňa (13029-kena-safari-pod-mount-kenya, 13030, 13031), Madagaskar (12454-madagaskar-na-kole, 12687-madagaskar-ostrov-lemuru), Mauricius (12666), Kapverdy (12311-kapverdy-turistika-a-koupani), Indonésie/Bali (12141-bali-a-lombok-vsemi-smysly, 12143-indonesie-velka-cesta), JAR (12469-jar-kapske-mesto-vino-a-narodni-parky), Filipíny (12528-filipiny-velka-cesta, 12698-filipiny-na-kole), Kostarika (12918-kostarika-a-panamsky-pruplav). Of the 24 profile countries, only 12 are represented in the 34 returned offers.

### 3.

The adapter's own doc-comment cites https://www.adventura.cz/zajezdy/12666-reunion-a-mauricius-turistika-a-koupani/ as its verified reference example — and that URL sits at index 46 of the sorted list, so it is never fetched in production. I fetched it manually: it is live and bookable (11. 11. – 23. 11. 2026, 13 dní, -1%, 79 800 → 79 002 Kč, code 26591601), and feeding the page to parseAdventuraDetail yields a perfect offer {country: Réunion, dep: 2026-11-11, nights: 12, board: BB, transport: flight, price: 79002, orig: 79800, pct: 1}. The parser is fine; the URL selection starves it. This is also the only Mauricius tour Adventura sells.

### 4.

EXOTIC_SLUG_TOKENS matches bare substrings and therefore misses Czech declined slug forms, hiding 6 in-scope tours BEFORE the cap is even reached: /zajezdy/12112-toulky-po-maledivach/ (slug has 'maledivach', token is 'maledivy'), /zajezdy/11268-treking-na-kapverdach/ ('kapverdach' vs 'kapverdy'), /zajezdy/12659-indonesky-lombok-vanoce-a-silvestr-na-kole/ and /zajezdy/12704-indonesky-lombok-na-kole/ ('indonesky' vs 'indonesie'), /zajezdy/10084-jihoafricka-republika-na-kole/ and /zajezdy/13042-jihoafricka-republika-vanoce-a-silvestr-na-kole/ (the 'jar' word-boundary token does not match 'jihoafricka'). Maledivy, Kapverdy, Indonésie and Jihoafrická republika are all in the exotika watch profile.

### 5.

Misleading log wording masks the blind spot: `adventura: 64 exotic tour URLs, capped at 25 (39 skipped this run)` (src/sources/adventura.ts:302). "this run" reads as round-robin sampling that will pick up the rest next time. Nothing rotates — the same 39 are skipped on every run forever. Anyone reading scan logs or a health alert would conclude coverage is eventually complete.

### 6.

board is 'unknown' on pages that explicitly state meals are NOT included, where 'none' is the correct value. transportAndBoard() is fed only the "V ceně zahrnuto" segment, so its `/bez\s*strav/` branch can structurally never fire. Example: /zajezdy/11893-havaj-velky-okruh-ctyrmi-ostrovy/ — included prose lists only "12x ubytování v apartmánech či hotelech" while the page's "V ceně nezahrnuto" block starts with "Stravování". 4 of 34 offers (3× Havaj + 1) carry board 'unknown' for this reason.

### 7.

country is null for Czech-declined titles because isKnownCountry() exact-matches the stripped first token. /zajezdy/11848-treking-na-reunionu/ (title "Treking na Réunionu") → country null even though 'Réunion' IS in the COUNTRIES dictionary, so this offer can never match the exotika profile's country filter. Same class of miss for 'Havaj' (Hawaii is a US state and USA is deliberately out of scope, so that one is arguably intended). 4 of 34 offers have country null.

WHY THE "INTENTIONAL DESIGN" DEFENCE FAILS (the strongest refutation available)
The header comment and docs/superpowers/plans/2026-07-04-dovolenky.md (Task 39) do document the cap: "the caller takes the first MAX_DETAILS (25)", "spec §16.1: 1 sitemap + ≤25 details ≈ 26 requests", and the header even records that 64 exotic URLs existed at the 2026-07-07 verification. So the request budget is genuinely intentional. But the documented intent is a *per-run request budget*, and that intent is fully satisfiable without a permanent blind spot: at the 2 h cadence (.github/workflows/scan.yml, `0 */2 * * *`, 12 runs/day), a rotating offset covers all 64 in 3 runs / 6 hours at the identical 26-requests-per-run footprint. Permanence is therefore a side effect of the ordering choice, not a consequence of the budget decision, and it is documented nowhere. Two further signals that it was not a considered decision: (i) the runtime log at line 302 reads "(${skipped} skipped this run)" — run-scoped phrasing that implies transient overflow rather than a fixed 61 % exclusion; (ii) the sibling adapter src/sources/fischer.ts:212-225 explicitly documents "Adapter-owned ordering: pick the MAX_TOURS earliest-departing tours ourselves rather than trusting the server's response order… so the 'top N' selection stays correct", i.e. the project's own convention is that a top-N cut must use a value-based criterion. Adventura's cut instead uses the site's internal tour id — effectively "the 25 oldest tour records" — with no rationale stated. The other three false-positive patterns do not apply: no missing-field issue, no teaser/term price mismatch, no dedupe overlap.

SEVERITY CORRECTED DOWN TO MEDIUM (report implies higher)
The coverage loss is real, silent and permanent, affecting the majority of the source's in-scope inventory. But its current blast radius is narrower than the report suggests: the `exotika` profile requires ≤ 60 000 CZK *and* ≥ 15 % real discount, while Adventura's product band is 63 k–144 k with 1–4 % first-minute discounts. The cheapest never-reached tour I sampled (Kapverdy, 64 152 CZK, -1 %) still misses both gates, so lifting the cap would most likely add zero profile matches today. The damage is to catalog completeness — 39 tours never enter the DB, so they are absent from the dashboard and from the market reference data — plus the fragility of a blind spot that would start costing real alerts the moment prices or the profile thresholds move. Also worth noting for the fix: the auditor's "~3.5 min for 64 pages" is accurate against the 3 s `min_request_gap_ms` in config/watch.yaml, but a rotating offset is the better fix than raising the cap, since the header (lines 21-24) records a deliberate §9 compliance deviation on a site whose robots.txt name-blocks the agent — keeping the per-run footprint at ~26 requests matters there.
