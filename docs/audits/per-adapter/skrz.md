# Audit: skrz (high)

## Shrnutí

skrz.ts fetches 9 hardcoded SSR listing pages on skrz.cz (/dovolena-more/destinace:{recko,turecko,egypt,bulharsko,thajsko,maledivy}, /pobyty/destinace:chorvatsko, /pobyty, /exoticka-dovolena), reconstructs the Next.js RSC flight payload from self.__next_f.push chunks, extracts the `deals` array with a string-aware bracket scan, and maps it field by field. Field mapping is accurate — I verified three live offers against their own detail pages and every field matched exactly, including the non-obvious priceFinal/persons division (skrz prints "od 8 305 Kč za 2 osoby" and the adapter correctly emits 4 153/person) and the derived claimedOriginalPrice (9 690 at 3 % → 9 990, exactly the "Původní cena 9990 Kč" the page shows). The problem is reach, not accuracy: every skrz listing page is server-capped at limit:24 with offset ignored, so 9 paths yield 202 unique offers against a site that reports 3 704 sea-holiday deals and 7 913 stays overall. The hardcoded slug list covers 6 of the 22 destinations skrz's own /dovolena-more facet exposes, and nine destinations holding 1 200 listed deals come back with literally zero offers. The price mix that does come through is healthy and representative (759 – 172 849 CZK, 40 exotic offers above 40k incl. Maledivy/Mexiko), so this is a wide-but-shallow slice, not a broken agency.

## Nálezy k opravě

### 1.

COVERAGE: nine destinations that skrz itself lists on /dovolena-more return ZERO offers from the adapter, because LISTING_PATHS has no slug for them. Site-reported totalItems (read from the RSC `dealsListing` object on each page): Itálie 403 (https://skrz.cz/dovolena-more/destinace:italie), Španělsko 383 (…/destinace:spanelsko), Tunisko 142 (…/destinace:tunisko), SAE 85 (…/destinace:spojene-arabske-emiraty), Portugalsko 76 (…/destinace:portugalsko), Malta 47 (…/destinace:malta), Kypr 27 (…/destinace:kypr), Albánie 26 (…/destinace:albanie), Černá Hora 11 (…/destinace:cerna-hora) = 1 200 deals, 0 in output. The adapter's live country tally is Řecko 24, Turecko 24, Egypt 24, Bulharsko 24, Chorvatsko 24, Maledivy 24, Thajsko 13, Česko 11, Kapverdy 9, Omán 6, Mexiko 5, Slovensko 4, Polsko 4, Slovinsko 2, Německo/Rakousko/Maroko/Mauricius 1 each — no Spanish, Italian, Cypriot, Tunisian, Emirati, Albanian, Montenegrin, Portuguese or Maltese offer at all. Fix is cheap: the destination facet URLs are enumerable straight out of the page blob, and each extra slug adds up to 24 offers.

### 2.

COVERAGE: the adapter is structurally capped at page 1. Every listing page returns `"limit":24,"offset":0,"totalItems":N`, and the server ignores the query param — I fetched https://skrz.cz/dovolena-more/destinace:recko?offset=24 and got byte-identical deal hashes to page 1 (24/24 overlap, first hashes nrqkWH, kMqzNC, kMNaBq…). So 9 paths × 24 = 216 max, 202 unique in practice, versus totalItems 3 704 on /dovolena-more (5.5 %) and 7 913 on /pobyty (2.6 %). Per destination: Řecko 24/655, Turecko 24/644, Egypt 24/261, exotika 24/305. Deeper pages are only reachable via the client-side infinite-scroll API, so the only practical lever is more slugs — which makes finding #1 the whole fix.

### 3.

LOW / efficiency: one of the nine slots is spent on the generic catch-all https://skrz.cz/pobyty (totalItems 7 913), whose page 1 is dominated by domestic wellness and 1-night stays rather than package holidays — it contributes the Česko 11 / Slovensko 4 / Polsko 4 rows plus two zero-night day trips (e.g. https://skrz.cz/voucher/IphMNP "Autobusem do Vídně: Dům moře a zábavní park Prátr", 759 CZK, nights 0). Swapping it for a real destination slug (Itálie or Španělsko, 400 deals each) would yield strictly more package inventory per request.

### 4.

LOW / normalization: skrz's breadcrumbs use "Česko" and "Německo", neither of which is a key in normalize.ts's COUNTRY_BY_KEY (the canonical entry is "Česká republika"), so normalizeCountry falls through to raw passthrough. Harmless today because profiles default to an empty `countries` list, but a profile written as `countries: ["Česká republika"]` would silently never match a skrz domestic offer, and computeMatchKey/computeHotelKey will not align skrz's "Česko" with any other source's "Česká republika".

## Adversariální ověření

- **VYVRÁCENO — neopravovat** (none): Every factual claim reproduces, but the framing as a defect fails on documented intentional design (false-positive category c).

LIVE CHECK (2 requests, Chrome 126 UA, 4s apart): https://skrz.cz/dovolena-more/destinace:recko returns an RSC blob with "dealsListing":{"limit":24,"offset":0,"totalItems":655}, 24 raw deals -> 24 mapped offers via parseSkrz. Refetching with ?offset=24 returns HTTP 200, still "offset":0, and 23/24 identical deal hashes in identical order (nrqkWH, kMqzNC, kMNaBq, ...); the single differing slot (IcgcMb -> ADolJp) is live inventory churn between fetches, which confirms it is the same page 1 rather than a different page. So the server does ignore the param, and src/sources/skrz.ts does 9 bare GETs with no pagination loop. robots.txt (fetched) does NOT disallow `offset` or `destinace:`, so the adapter is not declining pagination for politeness reasons. Searching the whole RSC blob found no /api/ or graphql endpoint, only LoadMore/ShowMore client component names -- consistent with deeper pages being reachable only through client-side RSC calls.

WHY IT IS NOT A DEFECT: the constraint and the chosen response are recorded in the project's own design spec BEFORE the adapter existed. docs/superpowers/specs/2026-07-04-dovolenky-design.md line 80, source row 9 (Skrz): "24 nabidek/URL, offset nefunguje -> pokryti sirkou URL" (24 offers per URL, offset does not work, therefore coverage by breadth of URLs). This is exactly the behaviour reported as a bug. The same depth-vs-breadth tradeoff is documented and accepted for another source -- src/sources/zajezdy.ts lines 9-10: robots blocks ?page=, so "coverage comes from breadth across these SSR listing pages (10 tourResults each) rather than pagination" -- while sources that do allow paging use it (src/sources/dovolena.ts buildListingUrl(destinationId, page)). So per-source pagination was decided deliberately, per source, not overlooked.

The adapter therefore exhibits no wrong data, no silent failure, and no unpulled lever: the 24-item cap is imposed server-side and cannot be lifted from the SSR path. The only actionable residue is "add more destination slugs", which the auditor themself collapses into finding #1 ("makes finding #1 the whole fix") and which the spec already anticipated (S16.2 / plan Task line 809: extend LISTING_PATHS with live-verified slugs -- which is why /exoticka-dovolena, thajsko and maledivy are present with a live-verification note in the file header). As an independent defect this is a duplicate of the slug-count finding relabelled as a structural cap.
