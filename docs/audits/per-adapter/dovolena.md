# Audit: dovolena (critical)

## Shrnutí

The adapter issues exactly 4 requests — GET https://dovolena.cz/api/trip-listing/tripListing?destination={4826|4813|4810|4830}&adult=2&page=1 (Řecko, Turecko, Egypt, Maledivy) — and takes whatever page 1 returns. Live it produced 40 offers, i.e. exactly the API's default perPage=10 per destination, out of 5626 hotels those same four destination ids actually hold (Řecko 2780, Turecko 1653, Egypt 810, Maledivy 383) = 0.71% coverage. Two independent multipliers are being left on the table: perPage is a supported parameter (verified: perPage=48 returns 48 hotels and drops totalPages 278→58) and the adapter never sets it nor pages; and the site sells ~41 country destinations, of which 4 are queried — Španělsko alone (id 4873) has 2020 hotels, Chorvatsko (4844) 476, Thajsko (4833) 729, so 3225 hotels sit in three unqueried countries versus 40 rows total from the adapter. Worse, the API's default ordering is strictly price-ascending (verified monotone 3769…7157 across 48 Greek rows), so the 10 rows per country are the absolute cheapest tail and the mid/high band is never sampled at all. On the DB red flag: the tripListing hotel object genuinely carries no date or nights field, so the module doc comment is factually right about that endpoint — but the conclusion "expected, not a parsing gap" is wrong, because the site exposes both a date/length query filter (honored live) and a per-hotel /api/trip-detail/tripDetail endpoint returning from, to, tripStayNights, operator and departure airport. Verified consequence: the adapter's 4713 CZK Club Sidar offer is a ONE-NIGHT stay departing from Vienna, presented with nights=null next to multi-night packages. Prices themselves are accurate (4713 matched the site exactly); country, stars, board, transport, dedup and error handling are all sound.

## Nálezy k opravě

### 1.

COVERAGE, critical — only page 1 at the default page size is ever fetched. buildListingUrl() hardcodes `page=1` and never sends `perPage`, so each destination contributes exactly 10 rows. Live totals for the adapter's own four ids: Řecko 2780, Turecko 1653, Egypt 810, Maledivy 383 = 5626 hotels, of which the adapter returns 40 = 0.71%. `perPage` is a first-class supported param: https://dovolena.cz/api/trip-listing/tripListing?destination=4826&adult=2&page=1&perPage=48 returned 48 hotels with totalPages 58 (vs 278 at perPage=10). No pagination loop exists in fetchOffers either.

### 2.

COVERAGE, critical — systematic cheapest-only bias. The API's default `order` is "recommended", which is in fact strictly price-ascending: the 48 rows from https://dovolena.cz/api/trip-listing/tripListing?destination=4826&adult=2&page=1&perPage=48 came back 3769, 3949, 4299, 4719, … 7157 with no inversion. Because the adapter takes only page 1, the 10 rows per country are the 10 absolute cheapest hotels in that country. The board therefore never sees dovolena.cz's mid or high band — e.g. Maledivy contributes only its 22.5k–27.8k floor while the site holds 356 of its 383 Maldives hotels above a 40 000 CZK group price (https://dovolena.cz/api/trip-listing/tripListing?destination=4830&adult=2&page=1&perPage=1&price=40000-2000000).

### 3.

COVERAGE, high — the hardcoded DESTINATIONS list is 4 entries against ~41 country destination pages the site actually sells (enumerated from https://dovolena.cz/sitemaps/dynamicPagesSitemap-0000.xml: albanie, bali, bora-bora, brazilie, bulharsko, cerna-hora, chorvatsko, cina, dominikanska-republika, filipiny, indie, indonesie, italie, izrael, japonsko, jordansko, kena, kolumbie, kostarika, kuba, kypr, malta, maroko, mauricius, mexiko, oman, peru, portugalsko, seychely, spanelsko, sri-lanka, thajsko, tunisko, vietnam, zanzibar, …). Measured live for three of them: Španělsko id 4873 = 2020 hotels (cheapest 5661 CZK/os), Chorvatsko id 4844 = 476 (5549), Thajsko id 4833 = 729 (16859). That is 3225 hotels in three countries — 80x the adapter's entire output — with zero representation. src/core/normalize.ts already lists Španělsko, Chorvatsko, Thajsko, Bulharsko, Kypr, Tunisko, Mauricius, Seychely, Zanzibar etc. in COUNTRIES, so the normalize layer is ready; only this adapter's DESTINATIONS array is narrow.

### 4.

FIELDS, critical — nights=null makes pricePerPerson non-comparable, and the missing value IS obtainable. The tripListing payload really has no nights/date key (hotel object keys are exactly: additionalInfo, address, destinations, fullGalleryFetched, gallery, gps, hotelId, labels, noStars, numberRating, priceInfo, title — unchanged even when date/length filters are applied), so the doc comment's premise holds for that endpoint. But https://dovolena.cz/api/trip-detail/tripDetail?hotelId=74687&adult=2 returns for the adapter's own Club Sidar offer: from 2026-10-12, to 2026-10-13, tripStayNights=1, tripLength=2, boarding "Bez stravy", operator "DERTOUR GmbH & Co. KG (DE)", personPrice 4713. The adapter publishes that as pricePerPerson=4713 with nights=null — a single night sold from Vienna, sitting on the board next to week-long packages. Second confirmation: hotelId 924336 "Medusa Aparthotel" (adapter pricePerPerson 3769) resolves to from 2026-10-07, to 2026-10-10, tripStayNights=3, operator "Čedok". Because the listing price is a min over terms of any length, the 40 rows silently mix 1-night and multi-night prices, the per-night discount ladder can never fire, and price-sorted views are actively misleading.

### 5.

FIELDS, high — the site accepts date and length filters that the adapter never sends, which would make nights known by construction without any extra per-hotel request. The frontend's own query serializer (webpack module 62884 in /_next/static/chunks/_app-70ff8b9f347911f4.js) builds tripListing calls from: adult, airport, board, ckFilter, date, destination, hotelCategory, hotelId, hotelName, kid, length, moreRooms, operator, perPage, price, sortBy, stopovers, tags, transfer, transport, tripType. `date` is dd.MM.yyyy-dd.MM.yyyy and `length` is nights from-to. Verified honored live: https://dovolena.cz/api/trip-listing/tripListing?destination=4826&adult=2&page=1&date=20.08.2026-10.09.2026&length=7-10 returned totalHotels 2622 vs 2780 unfiltered. Slicing the query by month and nights window would populate departureDate/nights for every row from the request itself.

### 6.

FIELDS, medium — departureAirport is null for 40/40 and tourOperator for 40/40, both available from tripDetail. The detail payload exposes transport.departureFrom and operator.name. Notably both offers I checked depart from "Vídeň" (Vienna), not a Czech airport — hotelId 74687 and hotelId 924336 both show departureFrom "Vídeň", carrier RYANAIR via https://dovolena.cz/api/trip-detail/tripDetail?hotelId=924336&adult=2. For a Czech deal board, presenting a cheap Vienna-departure offer with departureAirport=null is a material omission, and it correlates with exactly the cheapest tail the adapter is sampling.

### 7.

FIELDS, medium — locality collapses to a useless value for the largest destination. mapHotel takes destinations[1], which for Greece is only "Pevnina" or "Ostrovy" (Mainland/Islands) — two distinct values across all 2780 Greek hotels, so the locality discount tier degenerates into a second country tier there. The real locality is in the last destinations entry and in `address`: hotel 924336 has destinations [Řecko, Pevnina, poloostrov Chalkidiki a Thessaloniki, Kryopigi] and address "Řecko, Pevnina, poloostrov Chalkidiki a Thessaloniki, Kryopigi". Turecko ("Turecká riviéra") and Maledivy ("Kaafu Atol") are fine at index 1, so this is Greece-specific — but Greece is the biggest destination in the set.

### 8.

FIELDS, low — every offer's url is the raw JSON endpoint, e.g. https://dovolena.cz/api/trip-listing/tripListing?destination=4826&adult=2&page=1. A human who clicks it downloads JSON. The doc comment is right that the listing rows carry no hotel slug (hotel detail pages are /hotel/<country>/<slug>, 2000 of them in https://dovolena.cz/sitemaps/hotelsSitemap-0000.xml, with no id to join on), but the site's human-facing search page https://dovolena.cz/search-results?destination=4826&adult=2 does exist and takes the same params.

### 9.

FIELDS, low — priceTotal is null for 25 of 40 offers because priceInfo.group is absent on many listing rows (e.g. Turecko hotelId 74687, 586348). Where present it is exactly 2x regular; tripDetail returns totalPrice for the rest (9427 for 74687). Deriving total = pricePerPerson * adults, or reading it from detail, would close the gap.

### 10.

OPERATIONAL, low (not a data defect) — https://dovolena.cz/robots.txt contains `Disallow: /api/` for `User-agent: *`, which covers the /api/trip-listing/tripListing path this adapter depends on (and /api/trip-detail/tripDetail). Worth a conscious decision before scaling request volume on this source.

## Adversariální ověření

- **POTVRZENO** (high): CONFIRMED. Code check: buildListingUrl (dovolena.ts:103-105) emits only `?destination=<id>&adult=2&page=<page>` with no perPage, and fetchOffers (line 183) always calls it with literal page 1 — the `page` argument is dead parameterization, there is no pagination loop, and totalPages/totalHotels are not even declared in DovolenaTripListingResponse (lines 78-80). So each destination contributes at most the default 10 rows; 4 destinations = 40 offers.

Live re-verification (Chrome UA, 4 polite requests): destination=4826&page=1 -> perPage 10, totalPages 278, totalHotels 2779, 10 hotels (auditor's 2780 is same-day drift, immaterial). Same URL + &perPage=48 -> perPage 48, totalPages 58, 48 hotels returned, and the first 10 hotelIds are byte-identical to the default page-1 set ([924336,924338,924375,924368,924377,924498,924771,924340,924333,924404]) — ordering is stable, so the 38 extra rows are pure additional coverage at ZERO extra requests. page=2 -> 10 hotels with zero hotelId overlap with page 1 and prices continuing to ascend (5969..6539 after 5759), proving the skipped pages are real, distinct inventory. destination=4813&perPage=1 -> totalHotels 1653 (Turecko), matching the report.

All four listed false-positive escapes fail: (a) not a missing-field claim; (b) not a teaser/term price mismatch; (c) NOT documented intentional design — the module header (lines 8-56) explains destination-id discovery, the null departureDate/nights premise, the url fallback and the null claimed* fields, but says nothing about limiting to one page or about page size; tests/dovolena.test.ts:76 ("4 destinations x page 1") merely locks in the implementation; (d) not dedupe/overlap — page 2 overlaps page 1 by exactly zero hotelIds. The politeness defence also fails: design spec §9 budgets 50-150 requests per run across 9 hosts, and raising perPage adds no requests whatsoever.

Severity downgraded from critical to high: the rows the adapter does emit are correct (prices, country, stars, board, transport, dedupe all fine) and page 1 is price-ascending, so it captures the cheapest — most deal-relevant — slice per country; the app is blind, not broken. But the loss is structural, not just quantitative: with only the 10 cheapest hotels per country tracked, any hotel drifting out of that window is flagged inactive after 2 unseen runs and later reappears as a "new offer", which destabilises this source's price-drop history. Fix is a drop-in (add perPage plus a bounded page loop); per-response and cross-destination dedupe already exist in parseDovolena and fetchOffers.
